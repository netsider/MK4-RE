MK4 PC FILE FORMATS - A WALKTHROUGH FOR REVERSE ENGINEERS
Mortal Kombat 4, Windows port (1998, ported by Eurocom; published by Midway in North America and GT Interactive in
Europe). Notes by netsider, as of 2026-10-22.

INTRO
This file explains how to get from the retail game files to meshes, textures, sounds, animations and live game
state. It is self-contained and follows the order you would work in:
  1 open FILESYS.DAT -> 2 extract files -> 3 meshes/textures -> 4 sounds -> 5 videos -> 6 animations ->
  7 skeletons (link animations to meshes) -> 8 MK4.EXE code/tables -> 8A move scripts (which clips a move plays, in what
  order, with what velocities) -> 8B from button press to clip (command lists, strikes, reactions, fighter ids) ->
  9 runtime memory -> 10 physics -> 11 gaps -> 12 quick reference.
Every claim is tagged:
  PROVEN = checked against the game's code, data or a live run
  LIKELY = strong evidence, not fully traced
  GUESS  = unverified idea
No game data is included here: only offsets, structures and descriptions. You need your own copy of the game.
Tools: the tools\ folder next to this file holds netsider's scripts for each step (FILESYS.DAT extraction, GEO/texture
  export, ESF->WAV, the emulated animation decoder, the script/command-list decoder, live-game logger). They contain
  no game data and take your own file paths as arguments. See tools\README.txt for dependencies and usage.
Paths: <MK4 install folder> = wherever the game is installed (the installer lets you choose; no fixed default verified).
All integers are little-endian. "u32" = unsigned 32-bit, "s16" = signed 16-bit, etc. Offsets are hex unless noted.

==========================================================================================
0. FILES ON THE DISC / INSTALL
==========================================================================================
<MK4 install folder>\DATA\ (or the CD's DATA folder):
  MK4.EXE        main executable (Win32 PE, 1,182,720 bytes in the version studied)        PROVEN
  FILESYS.DAT    one container holding every mesh, texture, sound and the animation pack   PROVEN
  M_*.ECM        full-motion videos (M_INTRO, M_MIDWAY, M_EURO, M_KOMERC ... on the CD)      PROVEN (files exist)
Registry: HKLM\SOFTWARE\GT Interactive\Mortal Kombat 4\1.00 (WOW6432Node on 64-bit Windows),
  values Path (install folder), Setup, Config (binary saved settings incl. key bindings).        PROVEN
Config blob (0x24C bytes): byte i is XORed with (i*0x7B)&0xFF; after that u32 +0 = checksum = 0x43464729 + sum of
  signed byte[i] << (i mod 23) for i = 4..0x247 (mod 2^32). PROVEN (the stored checksum matched on the copy studied).
  s32 +0x240 / +0x244 = P1/P2 joystick selection (LIKELY). On modern Windows the value may sit under the per-user
  VirtualStore copy of that key. Tool: tools\mk4_config.py (read-only unless --reset-joystick).
The game runs fine under Wine (32-bit prefix) at 640x480x16, which is how the live work below was done.  PROVEN

==========================================================================================
1. FILESYS.DAT - THE CONTAINER
==========================================================================================
Layout (PROVEN):
  offset 0x0000: directory of exactly 799 entries, 12 bytes each (0x2574 bytes total), no header.
  after that:    file data (the first file starts at 0x3000 in the copy studied). No compression at container level
                 (files are stored as-is).
Directory entry (12 bytes):
  +0x0  u32  hash    hash of the file's original full path (see below)
  +0x4  u32  offset  absolute byte offset of the file inside FILESYS.DAT
  +0x8  u32  size    file size in bytes
There are no filenames in the container. Names are found by hashing candidate paths.

Name hash (PROVEN; reproduces all 799 entries with names recovered from strings in MK4.EXE):
  def fsys_hash(path):
      s = path.upper()
      h = 0; shift = 0
      for ch in s:
          b = ord(ch); if b >= 0x80: b -= 0x100        # signed char
          h = (h + (b << shift)) & 0xFFFFFFFF
          shift = shift + 8 if shift < 24 else 0
      return (h + len(s)) & 0xFFFFFFFF
Path prefixes the game used (PROVEN, dev paths still inside MK4.EXE):
  meshes/textures: "C:\SOURCE\MK4\WIN\GEOGFX\" + name   e.g. C:\SOURCE\MK4\WIN\GEOGFX\SZ_GEO.GEO
  animations:      "C:\SOURCE\MK4\WIN\ANIM\"   + name   e.g. C:\SOURCE\MK4\WIN\ANIM\ANIMDAT4.AP0
  sounds:          "c:\source\mk4\win\sound\pcmkNNNN.esf"  (try NNNN = 0000-9999; hash the same way)
  menu image:      "C:\SOURCE\MK4\WIN\menu.tga"
Worked example (pseudocode):
  fs = read("FILESYS.DAT"); h = fsys_hash("C:\\SOURCE\\MK4\\WIN\\GEOGFX\\SZ_GEO.GEO")
  for i in 0..798: (eh, off, size) = u32x3(fs, i*12); if eh == h: data = fs[off:off+size]
What is inside (PROVEN, by magic/content):
  674 x ESF sound files, 122 x GEO mesh/texture files (magic "v1.0", see section 3), 1 x MENU.TGA,
  ANIMDAT4.AP0 + ANIMDAT4.AP1 = 799. Every entry gets a name by hashing (AP0 and AP1 are directory entries #0 and #1).
  In the copy studied, AP0 sits at offset 12288 (size 2964) and AP1 at 15252 (size 1,138,516). (PROVEN for that copy;
  always look them up by hash.)
There are NO separate sprite or palette files: all 2D art is texture pages inside GEO files (section 3).  PROVEN

==========================================================================================
2. EXTRACTING
==========================================================================================
Procedure (PROVEN):
  1. Build a list of candidate names: scan MK4.EXE for strings ending in .geo/.GEO, .AP0/.AP1, .tga, and pcmk sound names.
  2. Hash prefix+name for each, match against the 799 directory hashes, write out data[off:off+size].
  3. Identify the rest by magic: "ESF" = sound, bytes "0.1v" (u32 0x76312E30) = GEO.
All 799 entries get names this way (tools\fsys_tool.py does steps 1-2: list or extract).
The game reads files by seeking into FILESYS.DAT (seen with strace under Wine): a live session loaded 57 named .geo files.  PROVEN

==========================================================================================
3. .GEO - MESHES AND TEXTURES
==========================================================================================
A GEO holds 3D parts and/or texture pages. Fighters, arenas, logos, HUD/fonts, VS portraits are all GEOs.  PROVEN
Header (PROVEN):
  +0x00 4 bytes  magic/version: bytes "0.1v" on disk, i.e. the u32 0x76312E30 = multi-char constant 'v1.0'
  +0x04 u32      tex_off  - offset of the texture section
  +0x08 u32      size
  +0x0C          block table starts (16-byte records), runs until a record fails the checks or tex_off is reached
Block record, 16 bytes (PROVEN; matches the open-source mk4decomp geo_mesh.py layout):
  +0x0 u16 type     byte 0 = draw flags, byte 1 = editor flag (see "Block types"); bit 7 of byte 0 = 2D sprite record
  +0x2 u16 count    number of triangles in this part (2D sprite records use these bytes differently, see below)
  +0x4 s32 a        vertex offset, relative to the address of THIS field   -> vtx_off   = rec + 4 + a
  +0x8 s32 b        strip-list offset, relative to this field              -> strip_off = rec + 8 + b
  +0xC s32 c        UV-row offset, relative to this field                  -> uv_off    = rec + 12 + c
Block types. The draw routine (VA 0x4BA01D) reads byte 0 of each record as flags (record = GEO + 0xC + 16 * part):
  byte 0 bit 0x80 set   = 2D SPRITE record (draw VA 0x4BB180), layout below. 0x81 = also draw the NEXT record
                          first (sprites built from two halves, e.g. a 128 + 72 px wide title).                 PROVEN
  otherwise 3D part, prepared by VA 0x4BB840, then one of four renderers:                               PROVEN (code)
    byte 0 & 0x40 -> VA 0x4BAD10: no lighting call, global brightness only. One such part in most arenas. LIKELY unlit
    byte 0 & 0x01 and object flag 0x80000 -> VA 0x4BA630 (special path only when global [0x541A10] is set,
                     else the default renderer).                                                     GUESS: optional effect
    byte 0 & 0x02 -> VA 0x4BAF60: per-vertex shade from depth (VA 0x4B2990). Only buyin_ge.          LIKELY depth-shaded
    else          -> VA 0x4BAA60, the normal lit renderer (VA 0x4B8C20). Types 0, 4 and 0x100 land here.
  byte 1 is NOT read by the draw or prep code, so type 0x100 (byte 0 = 0, byte 1 = 1) draws exactly like type 0.
    0x100 parts are small 3D pieces (shared_g 64, share2_g 22, also lair, prison, skull, tomb, wind), often 2-triangle
    quads or repeated copies of the same piece.  PROVEN (byte 1 unread); LIKELY editor/group flag; GUESS: effect frames
  Seen values:
  1   = fighter mesh parts                                                                  PROVEN
  0   = arena parts; in fighter GEOs a second set after the type-1 set with nearly the same counts. Exporters use the
        type-1 set for fighters                                                             LIKELY (second set = alternate/low detail, GUESS)
  0x4 = logo parts: midway_g.geo (3D Midway logo), attract_.geo (MK dragon medallion), MKlogo_g.geo (title logo).
        Plain 3D parts drawn by the normal lit renderer; exported with tools\export_pc_geo.py.          PROVEN
        MKlogo_g's 19 parts point their UVs at small colour swatches (u 241-253, v 109-113), so the mesh is
        flat-coloured and gets its look from lighting.  PROVEN (UVs) / LIKELY (look)
  0x2 = buyin_ge.geo only (two parts, then one type-0 part): the depth-shaded renderer.              PROVEN (code)
  0x40 = one part per arena: the unlit renderer.                                                     PROVEN (code)
  0x80 / 0x81 = 2D sprite records (VS portraits vs_*_ge, fonts, menus, theatre_, hstd_, eurocom_, logos, fatality
        art). The old reading "types 128..640 with count 0" was this record read as u16s.            PROVEN
Order of records: fighters = type-1 parts then type-0 parts; arenas = type 0 parts plus one 0x40; midway_g = two 0x4
  parts then sprite records; MKlogo_g = 19 x 0x4 then sprite records; attract_ = one 0x4 part then sprite records;
  buyin_ge = 0x2, 0x2, 0x0. Sprite records are skipped (not a list end) when scanning for meshes.  PROVEN
2D sprite record, 16 bytes (PROVEN from VA 0x4BB180 and the second path at VA 0x4BA4D1):
  +0x0 u8  flags      0x80 sprite; 0x01 = draw the next record too
  +0x1 u8  blend      & 3 -> table VA 0x4F41C0 {0, 1, 1, 3} -> polygon mode bits (<< 7):
                      0 = opaque, 1 or 2 = additive (saturating add, VA 0x4BFB80), 3 = 50/50 translucent
                      (VA 0x4BF8E0)                                                 PROVEN (code) / LIKELY (look)
  +0x2 u8  page       GEO-local texture page; mapped to a texture slot through the page table in the loaded file
  +0x3 u8  id         sequential number; not read by the draw code
  +0x4 s16 w, +0x6 s16 h     size on screen (can differ from the texture size: the game stretches)
  +0x8 s16 x, +0xA s16 y     offset on screen; x0 = x, x1 = x + w, y0 = y, y1 = y + h
  +0xC u8  u, +0xD u8 v      top-left texel in the page
  +0xE u8  tw, +0xF u8 th    texel width / height; u1 = u + tw, v1 = v + th
  This is the rectangle list that cuts single sprites out of the atlases (A3/A5 in MK4_TODO_UNKNOWNS.txt).
  Example: shared_g has a sprite shown 180 x 404 from a 23 x 51 texel rectangle.
Strip list at strip_off (PROVEN): repeated {u16 flag, s16 n}; n < 0 ends the list. Each strip has n+1 triangles and
  n+3 vertices. Sum of (n+1) == count, and vtx_off + 12*sum(n+3) == uv_off (use both as sanity checks).
Vertex, 12 bytes (PROVEN): s16 x, y, z, nx, ny, nz (position + normal). Game Y: negative = up.
  Divide by 100 to get a sensible scale for export (convention, not from the game).
UV row, 8 bytes per triangle (PROVEN): +0 u8 texture page index (GEO-local, 0 = first page), +1 u8 (not read by the
  game), +2..7 = u0,v0,u1,v1,u2,v2 (u8, /255).
  Byte 0 = page: VA 0x4BB943 "movsx ecx, byte [row+0]" -> page table -> polygon page bits; in all 107,176 rows of all
  GEOs byte 0 is below the file's page count.  PROVEN. (Earlier notes said byte 1 = page; that was wrong.)
  Byte 1: values 0-144 in runs, not the strip index; never read by VA 0x4BB840.  LIKELY editor-only (group/material id)
Decoding a part (pseudocode, PROVEN):
  cursor = 0; t = 0
  for (flag, n) in strips:
      for i in 0..n:
          a, b, c = cursor+i, cursor+i+1, cursor+i+2
          uv = row[t]; t += 1        # uv for a = bytes 2,3; b = 4,5; c = 6,7 (keep UVs tied to their vertex)
          order = [a,b,c]; if i odd: swap order[1],order[2]; if flag & 1: swap order[1],order[2]
          emit triangle(order)
      cursor += n + 3
Part order matters: in fighter GEOs each part attaches to one skeleton bone (section 7).  PROVEN
Arenas: all 15 arena GEOs are full 3D meshes, fully decoded; the block table is short (e.g. 7 blocks) and the last
  block's data ends exactly at tex_off. Triangle counts e.g. shaolin 881, ice_pit 708, forest 1411.  PROVEN
Fighter files: SC_GEO (Scorpion), SZ_GEO (Sub-Zero), LK_GEO (Liu Kang), JC_GEO (Cage), JX_GEO (Jax), JA_GEO (Jarek),
  TA_GEO (Tanya), RA_GEO (Raiden), SB_GEO (Sonya), plus RE/QC/KI/ME/NS/SH/GO/WG_GEO (Reptile, Quan Chi, Kai, Reiko?,
  Noob?, Shinnok, Goro, ...). First nine PROVEN by render; the rest LIKELY/GUESS from the two-letter codes.
  Alternate costumes use _a_/_e_/_g_/_m_ name variants (LIKELY).

Texture section at tex_off (PROVEN):
  (While loading, VA 0x4BC810 decodes page i into a free texture slot and writes {u16 slot, u16 slot} over the file's
  own bytes at tex_off + 8 + 4*i (0xFFFF = no free slot). That in-place table is the "page table" the draw code uses
  to turn a GEO-local page number into a slot. Page i's header is always read before it is overwritten.)  PROVEN
  +0x0 u32 ?            (skip)
  +0x4 u32 count        number of texture pages
  then count x { u16 width, u16 height, u32 packed_size, packed_size bytes of RLE data }
  Pages are typically 256x256. Pixel format 15-bit RGB 5-5-5: r = (c>>10)&31, g = (c>>5)&31, b = c&31.
RLE (PROVEN), per row, until width pixels are written:
  token = u16
  if token & 0x8000 == 0: one pixel of colour token
  else: colour = token & 0x7FFF; run = next u8; write colour run times
Transparency key: texel value 0x0000 (pure black) is transparent.  PROVEN
  The game draws in software (imports DDRAW and DSOUND, no Direct3D). Its textured span loops skip a texel whose
  16-bit value is 0, e.g. VA 0x4BF2B1 "mov ax,[edx+eax*2]; test ax,ax; je skip" (14 such loops, VA 0x4BEC00-0x4C2400).
  Bit 15 cannot be a key: in the RLE stream 0x8000 is the run flag. Near-black (e.g. 0x0001) is drawn.
Texture slots at run time (PROVEN): 16 slots of 256x256 16-bit pixels (pointer at [0xF83A00]). VA 0x4BE440(slot, x, y,
  w, h) copies a picture from the staging buffer into a slot (converted to 5-6-5 when [0x4FDCCC] is set). GEO pages go
  to free slots 0-14 (VA 0x4BC730 clamps to 14); slot 15 holds MENU.TGA.
2D art (HUD text, "FIGHT!", fonts, effects, gore, portraits, logos) lives in these pages as ATLASES; the rectangles are
  the 2D sprite records above.  PROVEN. (No sprite cutter is included yet.)
MENU.TGA is a standard TGA, 256x256 16-bit.  PROVEN
  Loaded once at start-up (init VA 0x4B1A70 -> VA 0x4B5580): the string "c:\source\mk4\win\menu.tga" (VA 0x4F40D0)
  is opened, the 18-byte TGA header skipped, 256 rows of 0x200 bytes read bottom-up into the staging buffer
  (VA 0xF4AF18), then VA 0x4BE440(15, 0, 0, 256, 256) makes it texture slot 15. The same routine first fills the
  key-name table at VA 0x4F3370 (MapVirtualKeyA).  PROVEN
  Content: an ASCII font, colour swatches and a blue dragon medallion: LIKELY the font and background of the PC set-up /
  key-configuration menus. Helper VA 0x4B50E0 then fills pixels that are 0 (GUESS: generated gradient tiles).
Tools: tools\export_pc_geo.py (GEO -> GLB + texture + preview; fighters use the type-1 parts, files without type 1,
  e.g. logos 0x4, buyin_ge, arenas, export all 3D parts; several pages -> one stacked atlas),
  tools\extract_textures.py (all texture pages -> PNG).

3A. ARENAS - DESCRIPTORS, SPAWN RECORDS, PROPS AND FLIPBOOKS
==========================================================================================
Static reading of MK4.EXE (2026-10-23). The arena GEOs (section 3) hold the parts; MK4.EXE says where each part goes,
which parts animate, and which parts are moved by code.
Arena number = [0x53849C] (LIKELY, section 9); the tables below are indexed by it.
Arena -> GEO (PROVEN): the start-up fixup table at VA 0x4D9460 fills one 64-byte descriptor per arena at
  VA 0x4E0948 + 64 * arena; words 0/1 = model handle. Names match the Kombat-Zone kode strings in the same order and the
  Practice "Background" list in reverse:
    0 Goro's Lair     lair_geo         6 Shaolin Temple  shaolin_
    1 The Well        well_geo         7 Living Forest   forest_g
    2 Elder Gods      elder_ge         8 The Prison      prison_g
    3 The Tomb        tomb_geo         9 Ice Pit         ice_pit_
    4 Wind World      wind_geo        10 "Skull"         skull_ge  (Practice-menu name; no Kombat-Zone kode; real name UNKNOWN)
    5 Reptile's Lair  snake_ge
Descriptor (64 bytes; pointers are stored as VA >> 2 and fixed up at start-up):
  w0, w1  model handle (both loaded, VA 0x429AB0)                                                    PROVEN
  w2      per-arena callback, called after the spawn (VA 0x429DE3)                                   PROVEN (call)
          tomb / skull: 0x429F10 = ret. wind: 0x429F20 starts processes 0x42A050 / 0x42A2B0 / 0x42A960
          (LIKELY the flying debris). shaolin: 0x42AC10 cycles the 16.16 list at VA 0x4E0E20 (0.90..0.99)
          (LIKELY light flicker). forest 0x42AB60; prison 0x42ACD0 (120-tick timer adding 0x41, GUESS light / fan);
          ice pit 0x42ACC0.
  w3      spawn list -> VA 0x407330 / 0x406DD0                                                        PROVEN
  w4      list -> VA 0x407620 (mostly zeros)                                                          UNKNOWN
  w5      animation list -> VA 0x4090E0                                                               PROVEN (format LIKELY)
  w7..w14 copied to globals / camera (LIKELY lighting / colour); w15 a function                       LIKELY / UNKNOWN
Spawn record, 28 bytes = 7 x u32 (PROVEN, VA 0x406DD0). It is the same record and the same builder routine as the skeleton
  bone records of section 7:
  +0x00 u32 flags. Bits 20-27 = animation group id (-> object +0x1C). Low 20 bits | 0x8000000 -> object +0x20.
        bit 0x08 clear = children follow (recurse); bit 0x10 = last sibling;
        bit 0x04 = no mesh / group node (LIKELY: every such record is a parent using part 0)
  +0x04 model handle (12 bytes {FILESYS entry ptr, loaded ptr, 0})
  +0x08 pointer to an AABB of 6 x s32 16.16 {x0, y0 (up positive), z0, x1, y1, z1}, or 0. AABB / 256 = the part's mesh
        extents exactly (e.g. lair part 0: x 4..4782, height 1258).                                  PROVEN
  +0x0C / +0x10 / +0x14 s32 x, y, z 16.16 -> object +0x30 / +0x34 / +0x38 (VA 0x406E31..0x406E7B)       PROVEN
        Applied as a translation of (x, y, z) / 256 mesh units: LIKELY (the Prison wall fan only lands on its wall this
        way). Non-zero in only 4 arenas. Records hold no rotation.
  +0x18 u32 part index = GEO block number (the draw reads record +0x18, VA 0x4BA000)                  PROVEN
Animation list (w5): zero-terminated u32 list of (group << 24 | script pointer); VA 0x4ABF50 splits the byte and
  VA 0x408B90 finds the object whose group equals it. PROVEN.
  Script: zero-terminated u32 list of (ticks << 24 | pointer to a 28-byte record whose +0x18 is the part to show) =
  a flipbook. LIKELY (consumer VA 0x409260 not followed to the end); 0 = loop (GUESS).
  Flipbooks found (groups: frames): Lair 1 (6 frames, 30-tick loop; flames LIKELY); Well 3 (10/10/10); Elder Gods one
  9-frame group + four 12-frame ping-pong groups with 60/120-tick holds; Tomb 4 x 6; Reptile's Lair 11 and 8;
  Shaolin 30; Living Forest 6 tree faces (ping-pong, 60-120-tick holds); Skull 4 groups sharing frames 2-7 plus a
  10-frame group (groups 2-4 have no spawned object - maybe spawned by code, UNKNOWN). Wind World, Prison and Ice Pit
  have no flipbooks: their motion is code-driven (UNKNOWN).
Texture key: arena pages use the same texel-0x0000 transparency key as everything else (section 3).  PROVEN
2D sprite records inside arena GEOs (wind 42, ice pit 1): how they are placed in 3D is UNKNOWN (wind records give x, y
  but no z).
Other 3D GEOs that are not arenas:
  ped_geo   handle used at VA 0x4A7300 next to "CONGRATULATIONS / IS TODAYS CHAMPION" -> champion pedestal  LIKELY
  ladder_g  loaded by VA 0x46420B; the ladder / tower screen                                           GUESS
  shinx_ge  spawned by VA 0x418498 (list 0x50B8F4); use                                               UNKNOWN
  cliff_ge, cage_end: record lists at 0x50228C / 0x502CB8 exist but nothing references them statically  UNKNOWN
  skbgnd_g  2D sprite GEO: the skull "PRESS KEY TO CONTINUE" screen (not a sky)                       PROVEN (content)
  opt GEO   2D sprite GEO: options / practice menu art                                                 LIKELY
  No separate sky GEO was found: backdrops are arena parts.                                            LIKELY
Still UNKNOWN: the real flipbook tick length (1 tick = 1/60 s assumed), w4, the code-driven motion (Wind World debris,
  Prison fan, Goro's Lair rock / heads pickups).
==========================================================================================
4. SOUNDS (ESF)
==========================================================================================
674 ESF files in FILESYS.DAT (PROVEN). Decoder found in MK4.EXE code at file offset 0xAFA8D.  PROVEN
Layout:
  +0x0 3 bytes "ESF", +0x3 u8 0x06
  +0x4 u32: low 24 bits = length, top byte = flags. For 8-bit PCM the length = data bytes (579/579 files); for ADPCM
           it is the decoded 16-bit PCM byte count, = 4 x data bytes (53 exact, 42 within a few bytes)
  +0x8 sample data
Flags (PROVEN; the loader VA 0x4B0600 returns the length as u32 & 0x1FFFFFFF and reads bits 29-31):
  0x20 set -> 4-bit IMA ADPCM, high nibble first, decodes to 16-bit PCM; clear -> 8-bit unsigned PCM
  0x40 set -> 22050 Hz; clear -> 11025 Hz
  0x80 set -> the sound LOOPS.  PROVEN: VA 0x4B0600 passes bit 31 out; VA 0x4C225A stores it as bit 0 of the
       sound slot's flag byte (+0x16 of a 28-byte slot at VA 0xF8D990); VA 0x4C2783 passes that bit as the flags of
       IDirectSoundBuffer::Play, i.e. DSBPLAY_LOOPING (1). The stop routines VA 0x4C2943 / 0x4C29DD act only on these.
       The 13 files: pcmk0101, pcmk0102 (8-bit 11025 Hz, 2.0 s / 4.0 s); pcmk2003, 2007, 2011, 2015, 2023, 2031, 2035,
       2039 (ADPCM 22050 Hz, 1.7-4.6 s); pcmk2070, 2071 (12 s), pcmk2081 (16 s).
       2003-2039 = sound codes 3, 7, 11, 15, 23, 31, 35, 39 = each arena music code + 2.  LIKELY arena ambience loops
Mono.
Which sound plays when (PROVEN from code): every sound goes through one routine, VA 0x4BD7C0, with a 16-bit sound code.
  code 0 or -1 = stop all sounds; -2 = stop the current one.
  code < 100 and in the music list at VA 0x4F5CC8 (1, 5, 9, 13, 21, 29, 33, 37, 62, 73, 78, 79, 80) = arena/menu music.
    Music is CD audio, not FILESYS.DAT (PROVEN): music code at position i of that list -> CD track i + 2 (track 1 is
    the data track), passed with a time in seconds from VA 0x4F5D00[track] to VA 0x4AC5E0, which plays it with
    mciSendCommandA (WINMM). Codes 1, 5, 9, 13, 21, 29, 33, 37, 62, 73, 78, 79, 80 -> tracks 2-9, 10, 12-15; times
    92 s for most, 122 (code 37), 16 (code 62), 90 (code 80) - LIKELY the play length. Arena -> code: VA 0x4DDD18.
  other codes <= 100 -> file pcmk(2000 + code); codes > 100 -> file pcmk(code / 5), e.g. 0xC21 = 3105 -> pcmk0621.esf.
  Check: the announcer name codes (section 8B, Shinnok) give pcmk0621, 0678, 0630 ... and those files say "Scorpion",
  "Raiden", "Sonya" ... in the right order (checked by speech recognition on 15 of 17), so the rule is PROVEN in use.
  Script sound ops and their tables: section 8A. tools\script_decoder_v3.py "sounds" and "movesounds" list them.
Tool: tools\esf2wav.py converts every ESF to WAV (the loop flag 0x80 is ignored; each file is written once).

==========================================================================================
5. VIDEOS (.ECM)
==========================================================================================
Fully decoded (PROVEN: output matches MK4.EXE's own routines byte for byte, run in an emulator).
Tool: tools\ecm_tool.py (info / frames -> PNG / audio -> WAV).
Player code: VA 0x4AFC60 (player), VA 0x4AFFC0 (file reader thread), VA 0x4BDD50 (frame decoder).  PROVEN

File header, 0xE18 bytes (PROVEN, all four files incl. M_INTRO):
  +0x0 4 bytes "ECM" 0x02
  +0x4 u32 frames
  +0x8 900 x u32  chunk sizes, one per chunk, rest 0 (chunks = ceil(frames / 15)). 0xE18 + sum(sizes) = file size exactly.
  (The old reading "8 + 4n + sum" was wrong; M_INTRO is not a different layout.)
Chunk = 1 second = 15 frames (the last may hold fewer):
  +0x0 4 bytes "SEC" 0x00
  +0x4 0x2B14 bytes  IMA ADPCM sound for this second: 22050 samples, high nibble first; predictor/index carry over from
       chunk to chunk (decoder VA 0x4AC190, tables VA 0x4F2520 steps / 0x4F24E0 index).  PROVEN (layout) / LIKELY (sound
       checked as smooth waveforms, not by ear)
  +0x2B18 EDL block holding the video data for the 15 frames
EDL block (Eurocom compressor; decoder VA 0x4B07E0):  PROVEN
  +0x0 "EDL" + method byte: bit 7 = big-endian header, low 7 bits 0 = stored, 1 = LZ + Huffman
  +0x4 u32 packed size (includes this 12-byte header)  +0x8 u32 unpacked size  +0xC bit stream
  Method 1 bit stream, read LSB-first. Repeat: 1 bit block type.
    1 = Huffman block: 9-bit count of literal/length code lengths, 9-bit count of distance code lengths. Each length:
        1 bit, if set a new 4-bit value follows, else the previous value repeats (the value carries between tables).
        Codes are canonical, ordered by (length, symbol); code bits are read one at a time, MSB of the code first.
        Symbol < 0x100 = literal byte; 0x100 = end of block; > 0x100 = match: length = LEN_BASE[k] + extra + 3,
        then a distance symbol: distance = DST_BASE[k] + extra + 1 (base / extra-bit tables: see
        tools\ecm_tool.py; same scheme as Zoinkity's public QuickBMS "EDL1" description).
    0 = stored block: 15-bit byte count, then raw bytes.
    After each block 1 bit: 1 = end of stream.
Unpacked video data ("MPC" 0x02):
  +0x4      256 x u16 palette, 5-5-5
  +0x204    15 frames x 4800 u16 block codes (frame k at 0x204 + k * 9600): 80 x 60 blocks of 4x4 pixels = 320x240
  +0x23484  codebook of 4x4 blocks, 16 palette-index bytes each
  code >= 65000 -> solid block of palette colour (code - 65000) & 0xFF; else codebook entry `code`.
  The game then softens solid blocks with a random pattern (VA 0x4BDD50, uses rand and a similarity table built from
  frame 0). ecm_tool.py leaves that pass out, so solid areas are flat; all other pixels match the game.  PROVEN

==========================================================================================
6. ANIMATIONS - ANIMDAT4.AP0 / ANIMDAT4.AP1 + THE EXE CLIP TABLE
==========================================================================================
There are exactly 612 clips, ids 0..611, shared by all fighters (one global table).  PROVEN
Any clip can be played on any fighter (575 clips use the 18-word human layout).  PROVEN
AP0 = index (PROVEN):
  +0x000 512 bytes: a 256-entry nibble/code table used by the decompressor (the game copies it to VA 0x5220D8)
  +0x200 records {u16 id_flags, u16 size}, one per clip in id order, ends with 0xFFFF.
         id_flags & 0x8000 = compressed; size = byte size of that clip in AP1.
  Sum of sizes == AP1 size exactly.
AP1 = clip data, concatenated in id order (clip k starts at sum of sizes of clips 0..k-1).  PROVEN

Clip descriptor table in MK4.EXE (PROVEN): file offset 0xFC76C = VA 0x4FDD6C, 612 x 12-byte records, followed by one
  more record (index 612) whose +0x0 is 0xFFFFFFFF (end marker). Record address for clip k = 0x4FDD6C + 12*k.
  +0x0 u32  clip data pointer. 0 in the file; at load time the game fills it with the address of the clip's data in the
            loaded ANIMDAT4.AP1 buffer. This is the pointer the frame decompressor (VA 0x4013A0) reads.        PROVEN
  +0x4 u32  frame count. Equals the decoded frame count for all 612 of 612 clips (e.g. intro clip 46 = 90 frames,
            win pose 114 = 100, Sonya's uppercut 293 = 20).                                                     PROVEN
  +0x8 u32  high 16 bits = node (word) count per frame: 18 for the 575 human clips; 24, 6, 4, 20, 9 and 13 for
            the rest. Uncompressed sizes match 4 * frames(+0x4) * nodes for all 41 raw clips.                  PROVEN
            bit 15 (0x8000) = "compressed" flag, copied in at load time from the AP0 list.                      PROVEN
            bit 0 (0x0001) is set on 27 clips: 43, 144-165, 535, 539, 606, 607. Meaning unknown. Most of them
            (144-165) are victim hit-reaction clips (GUESS: a "reaction"/"don't loop" flag).
  How the loader fills the table (PROVEN, code VA 0x401205-0x40130F):
    1. Walk the table until +0x0 == 0xFFFFFFFF and set every +0x0 to 0.
    2. Read ANIMDAT4.AP1 into one buffer (pointer kept at VA 0x5222D8).
    3. Walk the AP0 list at +0x200, {u16 id|0x8000, u16 size} until 0xFFFF. For each entry:
         rec+0x0 = current buffer position;  rec+0x8 = (rec+0x8 & ~0x8000) | (id & 0x8000);  position += size.
  Engine note: objects store addresses as (address >> 2) and read fields as [reg*4 + offset] (PROVEN). Example: a
    fighter's current clip is stored as (record address >> 2), see section 9. The PC code is LIKELY ported from the
    arcade (Midway Zeus) code; the arcade main CPU is a TI TMS320C3x-family DSP (MAME lists a TMS32032 at 60 MHz, older
    listings say TMS32031), whose 32-bit word addressing would explain the >> 2 storage (GUESS).
Frame layout (PROVEN):
  each frame = node_count s32 words. For human clips node_count = 18 -> 72 bytes/frame:
    word 0..2  root translation (signed, /256)
    word 3..17 one packed rotation per animated bone (15 bones)
Raw clips (41): s32 data[frames][nodes] directly.
Compressed clips (571): a bitstream decoded by MK4.EXE's routine at VA 0x4013A0 using the 512-byte AP0 table.
  The simplest reliable route is to run that routine in a CPU emulator (e.g. Unicorn): map the EXE, put the AP0 table at
  0x5220D8, point it at the clip data, read back frames*nodes words. This gives smooth, correct curves.  PROVEN
  A hand rewrite from the open-source mk4decomp C code gave wrong output for this build.  PROVEN
Packed angle word (PROVEN):
  x = w & 0x7FF; y = (w >> 11) & 0x7FF; z = ((w >> 22) & 0x3FF) << 1;  angle units = 2*pi/2048 (2048 = 360 deg)
Rotation order (PROVEN, from EXE code):
  ordinary bone local = Rz(-z) * Ry(-y) * Rx(-x)   (EXE 0x4BCE80)
  root local          = Rx(-x) * Ry(-y) * Rz(-z)   (EXE 0x4BD070)
  World = Parent * Local; bone position = parent position + parentWorldRot * joint offset.
Human word -> bone order: frame word (3+i) drives bone [3,2,0,4,7,5,8,6,9,11,14,12,15,13,16][i].  PROVEN
  (Readable: pelvis, chest, head, shoulders, elbows, wrists, hips, knees, ankles; elbows/knees mostly use x.)
A root rotation of (180,0,180) is just a 180-degree yaw, not upside down.  PROVEN
Playback rate: 1 frame per game tick, ~60 frames/s.  PROVEN (measured 61.3/s on the frame counter)
Worked example (pseudocode):
  ap0 = file("ANIMDAT4.AP0"); ap1 = file("ANIMDAT4.AP1"); exe = file("MK4.EXE")
  offs = cumulative sizes from ap0[0x200:]; rec = exe[0xFC76C + 12*k : +12]
  frames = u32(rec,4); nodes = u32(rec,8) >> 16
  if not compressed(k): F = s32 array(ap1[offs[k]:], frames*nodes)  else: F = emulate(0x4013A0, k)
  for f in frames: root = F[f][0:3]/256; for i in 0..14: (x,y,z) = unpack(F[f][3+i]) -> bone order[i]
Tool: tools\anim_emu.py does the emulate() step with the Unicorn CPU emulator ("info" lists every clip, "dump" writes
  the raw per-frame words of one clip).
Game-driven motion (LIKELY, strong): for travelling and airborne moves the clip gives only the pose; the game plays
  frames forward, holds one, may play them in reverse, and moves the body itself (section 10). So a clip exported
  "as is" can look short or odd. Clips are short pieces that game code chains together. The chaining, the
  attacker/victim pairing and the launch velocities are mostly data: see section 8A.
Throw-victim clips (144-165, 535, 606, 607): frame 0 is a stored thrower -> victim placement, not a pose; the game
  plays them from frame 1 (section 10B). PROVEN for Sonya's 156, LIKELY for the rest.

Skeleton tables live in MK4.EXE. Address mapping (PROVEN): code VA = file + 0x400C00; data VA = file + 0x401600.
Bone record, 7 x u32 (PROVEN):
  w0 = kind << 20 | flags        flags 0x100 = animated; 0x10 clear = push current node; 0x08 = end of branch (pop)
                                 (node builder VA 0x406DD0: kind = w0 sar 20 -> node+0x1C, flags = w0 & 0xFFFFF -> node+0x20)
  w1 = stream pointer
  w2 = pointer to the part's size box (7 words: min xyz, max xyz, 0; 16.16 fixed), or 0. It is 0 in every fighter
       skeleton checked; arena and creature skeletons use it.
  w3..w5 = joint offset, 16.16 fixed: 65536 = 1 game unit = 256 mesh units. Copied unchanged to node+0x30..0x38 by
       VA 0x406DD0 (PROVEN, code).
Joint-offset scale (PROVEN, code): the renderer (VA 0x4B9C7B-0x4B9CF9) computes each node's position as parent
  position + parent rotation * joint offset (VA 0x4BCF20 -> 0x4B2A90; the matrix is 4.12 fixed, 0x1000 = 1.0, so there is
  no scale), then shifts it right by 8 (VA 0x4B9CD8) and adds the part's s16 GEO vertices. So 1 raw unit of joint
  offset = 1/256 mesh unit, and offset x 256 / 65536 gives mesh units. Size boxes agree: SC_FAT2_.GEO parts measure
  about 250-256 mesh units per game unit of box size (LIKELY, data).
  An older factor of 270 (offset in game units x 270 = mesh units) came from the arcade (MAME) RAM skeleton dumps,
  where the same offsets are stored as floats with identical values (e.g. 0.58485 = 38328 / 65536). The 270 was
  never derived from code (GUESS: a visual fit). It is wrong for this build; use 256.
  w6 = node index
Parents come from walking the flags as a push/pop tree (rule above); this reproduces RAM-dumped trees exactly.  PROVEN
Animated records take frame words in order of their kind.  PROVEN
Mesh link: fighter GEO part i attaches to bone i of the 15-bone human skeleton. Size boxes (w2) can be compared to
  each GEO part's min/max (one axis sign-flipped) to identify which mesh a skeleton belongs to.  PROVEN (method)

8A. MOVE SCRIPTS - HOW THE GAME CHAINS CLIPS
==========================================================================================
Moves are not hard-coded. Each move runs a small bytecode "script" stored in MK4.EXE's data section (most of them in
VA 0x4D5000-0x4F0FFF). The script sets the fighter's clip, sets the OPPONENT's clip (reactions, throws), sleeps,
sets velocities and gravity, and jumps to other scripts or back into native code. Reading these scripts gives you
the clip order, attacker/victim pairs and launch physics without any live capture.                          PROVEN

Starting a script (PROVEN): native code does  push <script VA>; call 0x4594E0. That function stores
  (script address >> 2) in the fighter object at +0x48. There are 449 such call sites.
Interpreter (PROVEN): loop at VA 0x459500.
  word = next u32 of the script; opcode = word >> 24; jump to handler table[opcode] (table at VA 0x4E6970; opcodes
  0x00-0x7F, unused ones go to a default handler).
  The low 24 bits of the opcode word are an inline argument (usually only the low byte is used).
  Operand words, if any, follow the opcode word.
Clip operands are patched at load time (PROVEN): in the file every clip operand is 0. At start-up the routine at
  VA 0x41FCC0 walks two lists of (destination, value) u32 pairs in .data, list A at VA 0x4D6E80 and list B at
  VA 0x4DC3F8, each ended by a (0, 0) pair, and does  *destination |= value >> 2. So every patched pointer is stored
  packed (byte address / 4). When value is a clip record address, clip = (value - 0x4FDD6C) / 12. To read a script
  statically, apply both lists first.
  The same lists fill the per-fighter command tables (section 8B), goto and op-3C targets, the strike tables and
  single-clip slots in BSS (VA 0x5409xx-0x540Bxx) that native code reads. No other writer of these tables was found.
  In total the two lists hold 3,035 pairs; 801 of them name a clip, covering 451 of the 612 clips. 161 clips are never
  named this way (e.g. 310); some of those are named directly in native code (section 8).
Numbers (PROVEN by the uppercut check below): velocities and gravity are 16.16 fixed point (0x10000 = 1.0 per tick;
  6553 = 0.1). The raw integers are the same units as the live height/velocity fields in section 9.

8B. FROM BUTTON PRESS TO CLIP
==========================================================================================
This section follows one input all the way to the clips both fighters play:
  button press -> command table -> move word -> action table -> handler -> script -> attacker clips
  -> strike (hit box) -> reaction id -> reaction handler -> victim clips and physics.
Everything here is static data in MK4.EXE (after the start-up fixups of section 8A).

Step 2 - command tables (PROVEN). There are 16 BSS tables of 18 u32 entries (one per fighter id), 0x48 bytes apart,
  starting at VA 0x540448 (table i = 0x540448 + 0x48*i). Each button's input handler pushes one table, e.g.
  VA 0x45CAE0 pushes 0x540490.
  How a press reaches a table (PROVEN): the input routine VA 0x45C5B0 compares each input word with its previous value
  (0x45C6B0) and calls one handler per changed bit, from a press list and a release list:
    input word 0x4D30A4 (active low): press list VA 0x4E7250 - bit 0x10 HP, 0x20 BL, 0x40 HK, 0x01 joystick up;
      P2 uses the same bits << 8 (0x1000 HP, 0x2000 BL, 0x4000 HK, 0x100 up). Bits 0x02/0x04/0x08 are the other
      joystick directions (sequence codes 2/3/4, no table).
    input word 0x4D30A8 (active low): press list VA 0x4E72C8 - bit 1 LP, 2 LK, 4 RUN; P2 = bits << 4 (0x10, 0x20, 0x40).
      Release list VA 0x4E7300: bit 2 (P1 LK released) and bit 0x20 (P2 LK released).
    input word 0x4D30B0: list VA 0x4E7318 (six other handlers, 0x45D0B0-0x45D860; not fighter moves, not traced).
  The handler pushes its table and calls the matcher, 0x45DCC0 for P1 (fighter 0x5360D8, input history 0x528A98) or
  0x45DD20 for P2 (0x5360DC, history 0x53FD80).
    table      P1        P2        button / event
    0          0x540448  0x5406D0  joystick up (LIKELY by name: bit 0x01, the counterpart of D = bit 0x02)
    1          0x540490  0x540718  HP                                                  PROVEN
    2          0x5404D8  0x540760  LP                                                  PROVEN
    3          0x540520  0x5407A8  BL                                                  PROVEN
    4          0x540568  0x5407F0  HK                                                  PROVEN

    8          0x540688  0x540880  RUN                                                 PROVEN (bit), name LIKELY
  The P2 tables are filled by the same start-up fixups with exactly the P1 contents (144 of 144 entries equal;
  PROVEN statically).
  Entry [fighter id] points to that fighter's list in a command pool at VA 0x4E7340-0x4E7E90; an empty list is
  VA 0x5408D0.
  Command record = 3 u32: { sequence, extra, move word }. sequence = 0 ends the list; sequence = 0xFFFFFFFF means
  "button only" (no joystick motion). Otherwise each byte of sequence is one joystick step, LOW byte = EARLIEST step:
    0xDD = F (toward the opponent), 0xAA = B, 0x02 = D (PROVEN); 0x01 = U (LIKELY)

Step 3 - move word, bytes b3 b2 b1 b0 (PROVEN):
  b3  condition index into the check table at VA 0x4E7EA8. A check vetoes the move by clearing bit 0 of [0x54000C].
      0 = no condition. All used entries are read (PROVEN from the code; the names of the tested fields LIKELY):
      timers: T(n) = [0x538418] - [0x53FE68 + (2n + player) * 4] = ticks since event n. Pass if T >= limit:
        01 T(2)>=64  05 T(0)>=64  08 T(6)>=180  13 T(3)>=48  15 T(0x13)>=90  16 T(4)>=32  18 T(7)>=80  19 T(9)>=48
        1D T(0xA)>=80  1E T(0xB)>=70  1F T(0xC)>=60  21 T(0xD)>=60  22 T(0xF)>=80  23 T(0x10)>=90  31 T(0x12)>=80
        (a move whose condition uses timer n is a cool-down: the same special cannot be repeated too soon, LIKELY)
      own fighter: 02 state +0x74 == 0x2001; 03 +0x30 == 0 and anim flag bit 1 clear; 0E height <= -1.8 (in the air)
        (an earlier note said 02/03 test the opponent; they test the fighter itself)
      opponent: 07 opponent hit count (+0x7C) < 3; 0B hit-count compare; 09 state not 0x100D/0x1001/0x1002;
        0A state == 0x1001; 0F state != 0x100A; 11 state != 0x100B and a timer >= 120; 14 state not 0x1001/0x100D and
        a timer >= 90
      buttons held at the moment of the press (input words above; [0x540440] != 0 skips the test):
        2D BL+HK | 2C HP+HK+LP+LK | 2B HP+BL | 29 BL+HK+LP+LK | 27 BL+RUN (and [0x538678] == 0xE) | 26 BL+HK+LK |
        1C HP+BL+RUN | 10 BL+LP | 0D BL+LK | 17 BL+HK | 0C unclear (GUESS). 0D/17/1C/26/29/2B also need Up NOT held.
      fighter distance [0x533D5C] (LIKELY distance): 1B <= 1.0 | 2F >= 1.0 | 24 >= 1.3 | 25 >= 1.8
      arena [0x53849C]: 1A arena == 8 | 33 arena == 0. [0x53849C] is the ARENA number (LIKELY: it indexes the
        per-arena music codes at VA 0x4DDD18 and the sound-bank load). An earlier version said "finish him" - wrong.

  b2  selects the action table (decided by the dispatcher at VA 0x45F640):

        bit 3 -> aux table        VA 0x4E9FF0, 0x14 slots (empty: 5, 0x11, 0x13); crouching / air moves

      0x45F640 has NO bounds check and skips empty (0) entries (PROVEN).

  b1  input time window in ticks (how fast the sequence must be entered)
  b0  action index into the selected table
  The matched move word is written to the fighter object at +0x14 and the 0x45F640 process is started.
  Every fighter has misc 0x29 = weapon draw. Finisher slots (code PROVEN, names LIKELY):
    misc 0x40 (0x467D30 -> 0x43CC00; condition 1B or 25 = close/far): finisher clip slot = fighter id + 1 (ids 16 / 17

    misc 0x43 (0x467D20 -> 0x41FCF0 + 0x43BDC0; condition 1B): re-applies fixup list B, counts finishers for the winner

Step 4 - handler and script: the action table entry is a native handler that starts a move script (section 8A).
  Basic moves (punches, kicks, sweep, jump attacks) use the same handler for every fighter; op 3C inside the script
  picks the fighter's own clip.

Step 5 - strike (PROVEN). While the attack plays, the script (or native code) does a hit check with a strike record:
    script op 51 n / 50 w n -> table VA 0x540E78   op 52 n -> 0x540E28   op 53 n -> 0x540D38   op 5E n -> 0x540C80
    native code does the same with  mov [0x53FFEC], n ; call 0x48D4x0  (a fifth table, VA 0x540DC8, uses 0x48D460).
  Strike record, 24 bytes:
    +0x00..+0x0C  hit box x, y, w, h (16.16)                                         LIKELY
    +0x10 byte 0  reaction id when the hit lands on a standing victim ([0x540008] = 2) -> table VA 0x4ED4D0  PROVEN
    +0x10 byte 1  reaction id when the victim is airborne (0x48EEB0 test; [0x540008] = 3)                     PROVEN
    +0x10 byte 2  reaction id when the hit is BLOCKED                                                         PROVEN
    +0x10 byte 3  flags; bit 1 sets [0x540008] = 0x10 ("air")                         PROVEN (read)
    +0x14 s32     DAMAGE, 16.16 fraction of the health bar (0x10000 = whole bar), applied by 0x48DED0; a blocked hit
                  does damage x 0.2 (multiplied by 0x3333). E.g. Sonya low punch 5%, sweep 14%, roundhouse 18%.  PROVEN
    (code: VA 0x48D630-0x48D720). Each landed hit also increments the victim's hit counter +0x7C (used by condition 07).
    Throws and some specials do damage with script op 63 instead (e.g. the basic throw: 15% / 20% / 18% branches).
  Native moves keep their strike data in blocks right after the native op, parsed by 0x470CB0 or 0x470520:
    ground block = [strike n][strike fn][frames...][-1][next native]; air block = [a][strike n][strike fn][handlers...]

Step 6 - reaction (PROVEN). The reaction table at VA 0x4ED4D0 has 193 slots (ids 0x00-0xC0; 0x71-0x74 empty). Each handler sets the
